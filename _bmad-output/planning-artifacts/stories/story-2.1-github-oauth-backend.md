# Story 2.1: Backend OAuth2 — GitHub Login

Status: ready-for-dev

## Story

As a developer,
I want to log in to idp-app using my existing GitHub account,
so that I don't have to create and remember another username/password.

## Acceptance Criteria

1. `GET /api/v1/auth/github` generates a CSRF state token (`secrets.token_urlsafe(32)`), stores it in Redis under `oauth:state:{token}` with a 5-minute TTL, and redirects the browser to GitHub's OAuth consent page with the `state` parameter and scopes `read:user user:email`.
2. `GET /api/v1/auth/github/callback?code=&state=` validates the state token (Redis lookup), deletes the state key (single-use), exchanges the code for a GitHub access token, and fetches the user's GitHub profile.
3. On first login, a new user record is created in the database with: `full_name` from GitHub `name`, `email` from GitHub primary verified email, `avatar_url`, `oauth_provider="github"`, `oauth_provider_id` = GitHub user ID (as string), `hashed_password` = `secrets.token_hex(32)`.
4. On subsequent logins, `full_name`, `email`, and `avatar_url` are updated if changed at the provider.
5. After user upsert, an idp-app JWT (HS256, 30-minute expiry) is issued using the existing `create_access_token`.
6. The JWT is stored in Redis under `auth:exchange:{code}` with a 30-second TTL (`code` = `secrets.token_urlsafe(32)`).
7. The browser is redirected to `{FRONTEND_URL}/auth/callback?exchange_code={code}`.
8. If the state parameter is invalid or missing, the user is redirected to `{FRONTEND_URL}/login?error=invalid_state` — no user record is created or modified.
9. If GitHub returns an OAuth error (e.g. user denied), the user is redirected to `{FRONTEND_URL}/login?error=provider_denied`.
10. A structured log entry is emitted for each login attempt: provider, success/failure, user_id (on success), error_type (on failure). No tokens or secrets appear in logs.
11. The `users` table Alembic migration adds: `oauth_provider VARCHAR(50) nullable`, `oauth_provider_id VARCHAR(255) nullable`, `avatar_url VARCHAR(500) nullable`, and composite unique index `ix_users_oauth_provider_id` on `(oauth_provider, oauth_provider_id)`.
12. The `User` SQLAlchemy model is updated with the three new `Mapped` columns.
13. New Settings fields are wired and validated: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_OAUTH_REDIRECT_URI`, `FRONTEND_URL`.

## Dev Notes

- Use Authlib's `AsyncOAuth2Client` for async-compatible code exchange and profile fetch. Do not use blocking `requests` calls inside async route handlers.
- Scopes for GitHub: `read:user user:email`. GitHub's primary email requires a separate call to `https://api.github.com/user/emails` if the profile email is null — account for this.
- OAuth2 state token pattern: `oauth:state:{token}` in Redis. Use `await redis.set(key, "github", ex=300)` with NX flag to prevent double-writes.
- Exchange code pattern: `auth:exchange:{code}` → JWT string in Redis, `ex=30`, delete on first read.
- `hashed_password` for OAuth-only users: `secrets.token_hex(32)` — this is a random 64-character hex string that is NOT a valid bcrypt hash and cannot be used for password-based auth.
- User lookup on callback: query by `(oauth_provider, oauth_provider_id)` — NOT by email. Email can change at the provider; provider ID is stable.
- All new env vars must be added to `pydantic-settings` `Settings` class using appropriate validators. Access via `get_settings()` only.
- All dependencies injected using `Annotated[T, Depends(f)]` — see Architecture Section 3.2.
- `POST /auth/logout` (stateless, returns 200) can also be added in this story as it's trivial — it just returns 200 and the frontend clears its token.
